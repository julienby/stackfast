# Décisions du hub

Une ligne par arbitrage : date, choix, pourquoi, alternative écartée.

- 2026-09-29 — Image php-htmx : binaire officiel `yt-dlp_linux` 2026.08.19 épinglé par SHA-256 pour les transcripts YouTube ; paquet système écarté car sa version suit le cycle Debian, et installation Python écartée pour limiter les dépendances.
- 2026-10-02 — Les services propres aux apps ont leur Compose et joignent un réseau privé partagé avec leur stack ; `bin/deploy` les démarre avec un nom de projet unique. Intégrer leurs dépendances à l’image commune ou donner le socket Docker au web écarté. Remplace la décision du 2026-09-29 sur yt-dlp dans l’image PHP.

- 2026-10-23 — Un conteneur par app (`apps/<stack>/<slug>/compose.yml`, qui étend `stacks/<stack>/app.compose.yml`), tous sur l'image de leur stack. Isolation (code, secrets, réseau) pour faire travailler des agents sur une app sans voir les autres ; une app peut ajouter ses conteneurs. Écarté : un conteneur partagé par stack (une faille ou un agent voit tout) ; un build d'image par app (lent, 20 images à patcher). Remplace « un conteneur pour toutes les apps » du 2026-09-16 et les `services/*/docker-compose.yml` du 2026-10-02.
- 2026-10-23 — FrankenPHP (`dunglas/frankenphp:1-php8.5`) remplace Apache dans l'image php-htmx : un processus, config Caddyfile (remplace `.htaccess`), tourne en non-root sur :8080. Écarté : PHP-FPM + `php_fastcgi` du proxy (le proxy devrait voir le code de toutes les apps) ; mode worker (état persistant entre requêtes, incompatible avec le code actuel).
- 2026-10-23 — Conteneur d'app durci : lecture seule, uid de l'hôte via `user:`, `cap_drop: ALL`, `no-new-privileges`, plafonds mémoire/CPU/pids, `exec`/`system`/`proc_open` désactivés. Plus d'`entrypoint.sh` (le remappage de www-data ne sert plus). Écarté : root dans le conteneur ; garder `exec` « au cas où » (un besoin système = un conteneur dédié).
- 2026-10-23 — Un Caddy par instance (`proxy/compose.yml`, appartient au hub), config des apps générée (`proxy/generated.caddy`) depuis les apps et `proxy/domains`, validée avant rechargement. Le proxy rejoint le réseau de chaque app (aucune app ne voit les autres). Parcours d'adresse : `$APPS_HOST/<slug>/` → `stackfast domain` → les anciennes adresses redirigent en 301. Écarté : blocs écrits à la main (oubli, divergence) ; joker `*.domaine.fr` (certificat DNS-01, plugin Caddy par registrar) ; caddy-docker-proxy (composant de plus) ; nginx (une seule génération à maintenir).
- 2026-10-23 — Sécurité PHP = `stackfast update` (build `--pull` → tests de toutes les apps avec l'image candidate → bascule `:current`/`:previous` → recréation des conteneurs) + `stackfast audit` (version servie vs php.net, durcissement actif, conteneurs sur une ancienne image). Branche PHP fixée dans `stack.conf`, correctif jamais épinglé. Déclencheur : PHP2Shell (CVE-2026-109618/109619, 21/10/2026) ; `bin/deploy` faisait `--build` sans `--pull` et pouvait rebâtir sur une base vulnérable en cache. Écarté : épingler 8.5.x (un patch = un commit dans le hub) ; mise à jour automatique sans tests.
- 2026-10-23 — Secrets par app : `apps/<stack>/<slug>/.env` (env_file de son conteneur) ; le `.env` de l'instance ne garde que ses réglages (instance, `APPS_HOST`, uid). Écarté : un `.env` d'instance avec les secrets de toutes les apps (chaque conteneur et chaque agent les voyait).
- 2026-10-23 — Interface unique `stackfast <verbe>` : le client remonte jusqu'à l'instance et lance `bin/<verbe>`. Verbes : new, ls, domain, check, up, down, logs, shell, audit, update, rollback, deploy, proxy, migrate. `bin/new-app` devient `bin/new` (`stackfast new-app` reste accepté). Écarté : garder `bin/<script>` comme interface (on parle à des fichiers, pas à la stack).
- 2026-10-23 — Sessions PHP dans `data/.sessions` de l'app : `/tmp` du conteneur est un tmpfs effacé à chaque recréation (donc à chaque correctif). Écarté : volume Docker par app pour /tmp.
- 2026-10-28 — Apps autonomes : une app = un dépôt git qui contient tout (Dockerfile, compose.yml, Caddyfile, php.ini, socle `core/`, composer, contrat `AGENTS.md` + `.claude/`), construit sa propre image et tourne seule. La recette est copiée à la création, avec sa version dans `stackfast.json`. Seul Caddy est partagé sur le serveur. Pourquoi : lancer Claude Code dans l'app seule, aucun code commun entre apps, mises à jour de recette app par app. Écarté : image et socle partagés par stack montés dans toutes les apps (du 23/10 ; une modif touche tout, l'app n'est pas exécutable seule) ; monorepo d'instance contenant les apps (du 16/09 ; Claude voit tout). Remplace ces deux décisions.
- 2026-10-28 — Le code est copié, le savoir-faire est partagé : recettes et socle versionnés dans chaque app ; méthode, leçons et skills lus en direct depuis le hub. Correctifs de sécurité (PHP, Caddy) toujours en une commande (`update` reconstruit chaque image, sans toucher au code). Écarté : propager automatiquement chaque changement de recette à toutes les apps.
- 2026-10-28 — Développement sur le VPS, dans le dossier de l'app (`apps/<slug>/`, dépôt à part, ignoré par le dépôt de l'instance). Pourquoi : y lancer aussi les agents. Écarté : cloner l'app sur un poste comme mode principal (reste possible).
- 2026-10-28 — Mode worker FrankenPHP par défaut, avec `watch` (rechargement des workers à chaque modification de fichier, vérifié sur une fonction du modèle : pris en compte en moins d'une seconde). Socle sans `exit` (exception `HttpError` gérée par `handle()`), état par requête seulement, session uniquement à la demande. Mesuré sur 1 CPU, 50 connexions : accueil 1 270 → 3 394 req/s, détail 1 400 → 4 801 req/s, p99 58 → 28 ms ; 0 erreur, aucun état qui fuit (404 puis 200, CSRF, token API). Un seul réglage : le bloc `worker` du `Caddyfile` (FrankenPHP pose `FRANKENPHP_WORKER=1`). Le premier bench (classique, avant refonte) avait révélé une session créée par visite anonyme, 22 000 fichiers en 15 s. Écarté : mode classique par défaut (le gain worker est net et `watch` lève l'obstacle du développement à chaud).
- 2026-10-28 — CSRF sans session : cookie aléatoire SameSite=Strict + jeton HMAC (`APP_SECRET`) dans le formulaire (double soumission signée). Écarté : jeton en session (une écriture disque par visiteur anonyme, disque saturable) ; jeton signé sans lien avec le navigateur (réutilisable par un attaquant).
- 2026-10-28 — SQLite par défaut (recette php-htmx-sqlite) : `data/app.sqlite`, WAL, `busy_timeout`, migrations SQL numérotées suivies par `PRAGMA user_version`. Les helpers JSON restent pour les petits besoins. Écarté : ORM ou outil de migration externe.
- 2026-10-28 — Tailwind compilé par le binaire autonome (v4.3.3, sans Node) et htmx servi en local (4.0.0) ; plus de CDN. Pourquoi : le script `cdn.tailwindcss.com` compile dans le navigateur (lent, non prévu pour la production) et une app ne doit pas dépendre d'un CDN pour s'afficher.
- 2026-10-25 — Organisation d'app standard, MVC en fonctions : `routes.php` (table `'GET /items/{id}' => 'items_show'`), `models/` (métier pur), `controllers/` (une fonction par action, dont `api.php` et `mcp.php`), `views/<ressource>/` (fragment htmx = fichier en `_`), `init.php` (charge tout, partagé avec les tests). Une ressource = trois fichiers. Seule abstraction ajoutée : `Stack\dispatch()` (~12 lignes). `lib/` de l'app devient `models/` (plus de confusion avec le `lib/` de la stack). Écarté : classes, conteneur d'injection, couche « service », framework ; garder le routage en `match` dans `index.php` (monolithe dès 10 routes, pas de paramètres d'URL).
- 2026-10-25 — `lib/bootstrap.php` renommé `lib/stack.php` (le nom évoquait la bibliothèque d'UI ; le fichier porte le nom de son espace de noms `Stack\`). `bootstrap.php` reste en deux lignes (shim) pour les apps créées avant ; à supprimer quand plus aucune ne le charge.
- 2026-10-25 — Composer à trois niveaux : la stack (`composer.json` + `composer.lock` commité, installé dans l'image, requis par le Dockerfile : builds reproductibles), l'app (`stackfast composer <slug> …`, `vendor/` hors git, installé par `up` si absent ou lock plus récent), tes libs (helpers dans `stacks/php-htmx/lib` ; repo GitHub taggé en dépôt `vcs` ; `packages/` en dépôt `path` tant qu'elle évolue : documentés, pas encore éprouvés). Garde-fou : un paquet déjà dans le lock de la stack est refusé dans une app (deux versions chargées = conflit). `audit` passe `composer audit`. Écarté : un `composer.json` unique pour tout (une lib d'app grossit l'image de toutes) ; vendor dans l'image par app (un build par app).
- 2026-10-25 — `stackfast backup` / `restore` : une archive par exécution (data/ sans sessions, `.env` d'app, config d'instance, volume de certificats Caddy), relue après écriture, chmod 600, rotation `--keep`, chiffrement AES-256 si `BACKUP_PASSPHRASE`. `restore` ne remplace rien sans le mettre de côté (`backups/pre-restore/<date>/`), restaure l'instance seulement en restauration complète ou avec `--instance`, et marche sans `.env` (serveur neuf). SQLite copiée par `sqlite3 .backup` dans le conteneur (écrit dans `data/` : `docker cp` ne lit pas le tmpfs). `audit` signale l'absence de sauvegarde récente. Écarté : sauvegarder le code (git le fait) ; envoi distant intégré (rsync/rclone font mieux, chiffrement suffisant) ; `.backup` dans `/tmp` du conteneur (illisible depuis l'hôte).
- 2026-10-23 — Agents isolés (`stackfast agent`) : une sandbox par agent (copie de l'app + stack/contrat en lecture seule, conteneur sans privilège, réseau à lui, preview `/_preview/<slug>/<nom>/` sous mot de passe), image = la stack + git + node + Claude Code (cible `agent` du Dockerfile). L'agent sert son app et lance ses tests lui-même : pas de socket docker. Écarté : `git worktree` (partage le `.git`, donc l'historique des autres apps) ; agent à la racine de l'instance avec règles écrites (rien ne l'empêche de lire `.env`) ; socket docker dans la sandbox (équivaut à root sur l'hôte).
- 2026-10-23 — Retour des changements par comparaison de fichiers, jamais par git : `apply` fait une fusion à 3 voies (`git merge-file`) entre la base de départ, la copie de l'agent et l'instance, limitée à `apps/<stack>/<slug>/`, refuse les liens symboliques ; l'hôte ne lance jamais git sur le dépôt que l'agent contrôle (config/hooks piégés). Écarté : `git fetch`/merge depuis la sandbox ; `patch` (pas de fusion de deux agents sur un même fichier).
- 2026-10-23 — `agent run` = `claude -p --dangerously-skip-permissions` (la sandbox est la frontière) ; `agent shell` garde les confirmations. Compte Claude passé par `AGENT_ANTHROPIC_API_KEY` / `AGENT_CLAUDE_CODE_OAUTH_TOKEN` du `.env` d'instance, jamais dans la copie ; secrets d'app pour agent seulement via `.env.agent`. Écarté : monter `~/.claude` (credentials et historiques de tous les projets).
- 2026-10-23 — `stackfast sync` met les stacks à jour sur place (fichiers remplacés, dossiers conservés) : supprimer-recréer `stacks/<stack>/lib` cassait son montage dans les conteneurs en marche (apps « unhealthy » jusqu'au prochain `up`). Écarté : exiger un `deploy` immédiat après chaque sync.
- 2026-08-20 — kit php-htmx : un repo par app, libs copiées, pas extraites. **Remplacée le 2026-09-16.**
- 2026-09-16 — Un monorepo par VPS (instance), multi-stack : `apps/<stack>/<slug>`. Une seule chose à déployer, un seul contrat à lire. Écarté : un repo par stack ou par app (autant de repos que de SaaS).
- 2026-09-16 — Composer et helpers partagés par stack (`stacks/<stack>/lib`, namespace `Stack\`). Le namespace lève le risque de collision qui justifiait la copie. Écarté : copier `lib/` dans chaque app.
- 2026-09-16 — JSON à plat par défaut (`data/*.json`, écriture atomique), SQLite quand l'app est validée. On voit les données, on itère. Écarté : SQLite + migrations dès le départ.
- 2026-09-16 — Préfixe d'URL fourni par le proxy via l'en-tête `X-Base-Path` (Caddy ou nginx), sinon déduit de `SCRIPT_NAME`. Bascule sous-répertoire → domaine sans toucher au code. Écarté : variable d'env par app (impossible avec un conteneur partagé).
- 2026-09-16 — Tests PHP CLI sans framework (`tests/*_test.php`, ok/FAIL, exit 1), une commande `bin/check` pour toutes les stacks. Écarté : PHPUnit (dépendance, config, pas lisible par tout le monde).
- 2026-09-16 — Secrets dans `.env` gitignoré (une variable par app, préfixe `<SLUG>_`), passés par `env_file`. Écarté : valeurs par défaut dans compose.
- 2026-09-16 — Apache tourne avec l'uid de l'hôte (`HOST_UID/HOST_GID`) : `data/` bind-monté reste lisible et éditable des deux côtés. Écarté : `chown www-data` / `chmod 777`.
- 2026-09-16 — Chaque app expose `/api` et `/mcp` par défaut, scaffoldées même vides (200, liste vide). Agentic first : jamais à rajouter après coup. Écarté : les créer seulement quand l'app en a besoin.
- 2026-09-16 — `/api` et `/mcp` répondent même vides plutôt que 404 : un client (humain ou agent) découvre toujours la surface, même sans endpoint déclaré. Écarté : 404 tant qu'aucun endpoint n'est enregistré.
- 2026-09-16 — Un seul bearer token par app (`<SLUG>_API_TOKEN`, `.env`) protège `/api` et `/mcp` ensemble. Une app = un consommateur (l'app elle-même ou son agent), pas de raison de séparer. Écarté : un secret partagé au niveau instance ; deux tokens distincts par surface.
- 2026-09-28 — Client `stackfast` : clone permanent du hub dans `~/.stackfast`, CLAUDE global et skills reliés par liens symboliques. Modifier en local = modifier le clone ; git fait le sens retour. Écarté : copies posées par `install.sh` (on ne sait plus ce qui a changé, ni où).
- 2026-09-28 — Client et contenu dans le même repo, un seul `git pull` met à jour les deux. Écarté : deux repos (utile seulement si d'autres personnes ont leur propre contenu).
- 2026-09-28 — VPS en lecture seule sur le hub (`stackfast pull` seulement). La méthode s'édite en local. Écarté : deploy key en écriture sur chaque VPS.
- 2026-09-28 — Skills ajoutées une par une (`stackfast skill add`), liées dans `~/.claude/skills/<nom>`. Écarté : lier tout `~/.claude/skills` (le hub récupérerait les skills de tiers).
- 2026-09-28 — `stackfast sync` protège les modifs locales par un manifeste de sommes (`stacks/<stack>/.stackfast-sums`, sha256 hors `vendor/`) : écart depuis la dernière sync → stop et liste, `--force` écrase. La sync retire aussi les fichiers supprimés du hub. Écarté : `diff` hub/instance (bloque aussi les vraies mises à jour du hub) ; `git status` de l'instance (dépend d'un commit que l'on ne maîtrise pas).
- 2026-09-28 — Stack php-htmx en PHP 8.5 (`php:8.5-apache`), dernière version. PDO et pdo_sqlite viennent de l'image : plus de `docker-php-ext-install pdo pdo_sqlite` ni de `libsqlite3-dev`. Écarté : rester en 8.4.
- 2026-09-28 — Image php-htmx sans extension LDAP : aucune app ne l'utilise. Écarté : la garder « au cas où ».
- 2026-09-28 — `stacks/php-htmx/lib` vient seulement du volume (lecture seule), plus de `COPY lib` dans le Dockerfile : une seule source, pas de rebuild pour un changement de lib. Écarté : copie dans l'image (deux versions possibles, l'image masquée par le volume).
- 2026-09-28 — Plus de `APACHE_RUN_USER`/`GROUP` dans le compose : `entrypoint.sh` remappe déjà `www-data` à `HOST_UID`/`HOST_GID`. Écarté : les deux mécanismes en double.
- 2026-09-28 — `bin/check` sans php local traduit chaque argument chemin vers le conteneur (pas seulement le premier) : le lint échouait sur un VPS sans php. Écarté : exiger php sur l'hôte.
- 2026-09-28 — `stackfast push` fait `pull --rebase` avant `push` : deux machines qui poussent ne se bloquent plus. En cas de conflit, git s'arrête au milieu du rebase et on résout dans le hub. Écarté : `pull --ff-only` (échoue dès que le hub a divergé) ; merge commit.
- 2026-09-28 — `bin/new-app` écrit le token dans `.env` s'il existe, sinon l'affiche seulement : un oubli de copie donnait un 401 silencieux. Écarté : créer `.env` (il doit venir de `.env.example`).
- 2026-09-28 — Politique de modèle en 3 niveaux (rapide / standard / fort) dans le CLAUDE global, avec règles pour monter et descendre. Claude change de niveau par sous-agent, Codex par `--profile`. Écarté : un modèle unique pour tout ; changement de modèle automatique (aucun outil ne le fait).
- 2026-09-28 — Compose php-htmx : `name: ${PHP_HTMX_CONTAINER:-php-htmx}`. Deux instances sur une machine ont deux projets compose et ne se détruisent plus. Écarté : `-p` dans `bin/deploy` (un `docker compose` lancé à la main l'oublie).
- 2026-09-28 — Profils Codex `rapide`/`fort` dans `INIT/codex/*.config.toml`, reliés par `stackfast link`. Effort seulement (`low`/`high`), pas de nom de modèle. Écarté : `[profiles.x]` dans `config.toml` (refusé par Codex 0.154) ; écrire dans le `config.toml` de l'utilisateur.
- 2026-09-28 — `stackfast push` : un `pull --rebase` qui échoue affiche la marche à suivre. Message neutre (« Si conflit ») car un échec réseau passe par le même chemin. Écarté : `git rebase --abort` automatique (perd le travail en cours de résolution).
- 2026-09-28 — Passe sur le CLAUDE global : moins de gras, règle d'ambiguïté unifiée, plan pour Codex, critère « Lesson générale ». Écarté : ajouter des règles sans erreur observée.
- 2026-09-28 — `stackfast sync` gère aussi `bin/` et `.claude/` de l'instance : fichiers du hub posés un par un, manifeste `.stackfast-sums` à la racine, même règle que les stacks (écart → stop, `--force` écrase, fichier retiré du hub → retiré). Sans manifeste : stop si un fichier diffère du hub. Écarté : vider `.claude/` (perd `settings.local.json`) ; passer en silence sans manifeste (perd une modif locale).
- 2026-10-02 — Skill globale `explain` (`INIT/skills/explain`) : page HTML autonome avec diagramme SVG, écrite dans `~/.cache/explain/<projet>/`, hors de tout repo (rien à ignorer, rien à committer). Idée venue du tweet de Karpathy sur la compréhension des sorties LLM. Écarté : `.explain/` dans chaque projet (oubli de `.gitignore` = commit) ; vidéos explicatives (dépendances lourdes, besoin non observé) ; règle « 80 % STE » (pas d'erreur observée).
- 2026-10-03 — Le code propre à une stack sort de `instance/bin/` : `bin/check` appelle `stacks/<stack>/check`, `bin/new-app` appelle `stacks/<stack>/post-new-app` s'il existe. `bin/deploy` était déjà neutre. Pas d'interface plus large tant qu'une seule stack existe. Écarté : attendre la 2e stack (elle aurait dû défaire le mélange) ; renommer `INIT/` en `core/` (sans erreur observée).
