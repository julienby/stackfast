Ton contrat
avec Claude Code.

Le CLAUDE.md n'est pas une doc — c'est un journal de contraintes chargé à chaque session. Ce guide explique comment le lire, le faire vivre, et travailler à moindre coût avec Opus 4.8.

Le principe

Une règle = une erreur évitée

La méthode (d'après Cherny & Karpathy) tient en une phrase : on n'ajoute une ligne que pour empêcher une erreur déjà observée. Si une règle ne répond pas à « quelle erreur précise ça évite ? », elle n'a rien à faire là.

Concrètement : ne pré-écris pas 800 lignes de règles. Tu as une bonne base ; la vraie valeur vient du réflexe, pas du volume. Objectif — rester sous ~100 lignes et élaguer ce qui ne sert plus.

Deux fichiers, deux rôles

Ce que tu maintiens vs ce qui se maintient seul

Un seul fichier est à toi. L'autre est un tampon que Claude gère pour rendre les sessions jetables sans perte.

CLAUDE.mdtoi

Les règles. Chargé auto au début de chaque session — elles s'appliquent sans rappel. C'est le seul fichier que tu édites à la main.

PLAN.mdclaude

Le plan validé d'une tâche en cours + son avancement. Claude le crée et le met à jour seul. À gitignore. Permet de couper une session sans re-briefer.

La boucle de travail

Plan → exécute → commit → clear

  1. Tu demandes une tâche non triviale → Claude passe en plan mode et présente le plan.
  2. Tu valides → Claude écrit le plan dans PLAN.md et exécute.
  3. Tâche finie → tu vérifies le diff → commit.
  4. Tâche indépendante suivante → /clear, contexte frais.
« Tâche indépendante » ≠ code indépendant

Le test : si un nouveau dev pouvait attaquer la tâche suivante avec juste le repo + une phrase de consigne — sans lire l'historique du chat — alors c'est indépendant. Le résultat d'une tâche finie vit dans le code commité, pas dans la conversation. L'historique devient du poids mort qu'on repaye à chaque message.

Maîtriser les coûts — Opus 4.8

Le coût vient du contexte relu

Pas de ce que le modèle écrit, mais de ce qu'on lui fait relire. Trois réflexes :

/clear

Entre tâches indépendantes. Le levier n°1. PLAN.md rend la coupure indolore.

/compact garde le plan, les décisions d'archi et les fichiers modifiés

Quand tu dois continuer. L'instruction évite de garder du bruit dans le résumé.

/model sonnet

Les journées mécaniques (refactos guidés, tests, docs). Le CLAUDE.md rend le downgrade sûr : Sonnet suit les mêmes règles.

Le mécanisme vivant

La section Lessons

C'est le cœur du système. Chaque bêtise de Claude devient une règle qui l'empêchera de recommencer :

1. tu corriges l'erreur
2. → « ajoute la règle qui l'aurait évitée à CLAUDE.md »
3. → le fichier devient ta mémoire institutionnelle

Élague aussi, dans l'autre sens : une règle qui ne sert plus, on la supprime.

Quand ça grossit

Découper avant que ça pèse

  • .claude/rules/ — éclate en code-style.md, htmx-patterns.md, sqlite.md, référencés via @imports. L'essentiel dans le fichier principal, le détail à côté.
  • Slash commands pour les routines : /new-endpoint (route + partial HTMX + test), /migration (schéma + vérif), /techdebt (fin de session, traque la duplication).
  • Hook PostToolUse — Ruff (format + lint) en auto après chaque édition. Règle le formatage raté, évite les échecs CI, sans y penser.
