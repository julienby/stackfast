Tutoriel · du premier jour à la production

Du serveur vide au site en ligne

stackfast fait d'un serveur une usine à sites. Une commande crée une app, la met en ligne en HTTPS, la sauvegarde, la met à jour quand une faille PHP sort, et laisse des agents y travailler sans qu'ils voient le reste. Ce tutoriel suit le chemin complet, avec ce qui se passe sous le capot à chaque étape.

  • 1InstallerDocker, un enregistrement DNS, une commande. Un dossier d'instance par serveur.
  • 2Premier projetstackfast new, puis un nom de domaine. Environ une minute la première fois.
  • 3Faire vivreDévelopper, agents, sauvegardes, correctifs de sécurité, mises à jour.

La carte

Quatre mots suffisent pour tout comprendre. Le reste du tutoriel ne fait que les utiliser.

MotCe que c'est
HubLe repo stackfast sur GitHub : la méthode de travail, les stacks, le gabarit d'instance et la commande stackfast. C'est lui que tu fais évoluer.
InstanceUn dossier sur un serveur, qui est un dépôt git. Elle reçoit les stacks du hub et héberge tes apps. Un serveur, une instance.
StackUne façon de faire des apps. Aujourd'hui php-htmx : PHP 8.5 sur FrankenPHP, htmx, Tailwind. Elle appartient au hub : l'instance ne la modifie pas.
AppUn projet, dans apps/<stack>/<slug>/. Son conteneur, son .env, ses data/, son code.

Une fois en route

Voici ce qui tourne sur le serveur quand tout est installé. Un seul point d'entrée, et une cloison étanche entre les apps.

  • Un Caddy par instance. Il est le seul à publier des ports (80 et 443). Il obtient et renouvelle les certificats tout seul.
  • Un conteneur par app. Même image que sa stack, système de fichiers en lecture seule, utilisateur non root, aucune capability, mémoire et processus plafonnés.
  • Un réseau privé par app. Seul Caddy les rejoint toutes. Une app compromise ne voit ni le code, ni les données, ni les secrets des autres.
  • Les secrets restent par app. Chaque app lit son propre .env ; l'instance n'a que ses réglages.

Installation

Compte une dizaine de minutes, dont l'attente du DNS. Tout se passe sur le serveur.

Avant de commencer

Il te fautDétail
Un serveur LinuxUbuntu ou Debian, accès SSH, un compte avec sudo.
DockerDocker Engine avec docker compose v2.17 ou plus. Étape 1 ci-dessous.
git, curl, opensslPresque toujours déjà là. sudo apt install git curl openssl sinon.
Les ports 80 et 443 libresLe Caddy de stackfast les prend. Un autre Caddy ou nginx doit être arrêté avant (voir l'encadré plus bas).
Un nom de domaineDont tu peux modifier le DNS.

  1. Installer Docker

    curl -fsSL https://get.docker.com | sh
sudo usermod -aG docker $USER      # puis déconnecte-toi et reconnecte-toi

    Vérifie avec docker version et docker compose version, sans sudo.

  2. Pointer un nom vers le serveur

    Chez ton registrar, ajoute un enregistrement pour l'hôte des apps en incubation. Ce nom ne servira qu'à tester ; le vrai domaine du site viendra plus tard, sur le même principe.

    NomTypeValeur
    apps.tondomaine.frA (et AAAA si IPv6)l'adresse IP du serveur

    Le certificat sera demandé au premier accès, donc le nom doit déjà répondre. Attends la propagation avant l'étape 5.

  3. Installer stackfast et créer l'instance

    curl -fsSL https://raw.githubusercontent.com/julienby/stackfast/main/INIT/install.sh | sh -s -- ~/mon-instance

    Le script est idempotent : tu peux le relancer sans risque. Voici ce qu'il fait.

    Il laisse ceci sur le disque :

    ~/.stackfast/             # le hub (clone git, c'est lui qu'on met à jour)
~/.local/bin/stackfast    # la commande (ajoute ~/.local/bin à ton PATH si besoin)
~/.claude/CLAUDE.md       # la méthode, en lien vers le hub
~/mon-instance/
  AGENTS.md  DECISIONS.md  .env.example
  bin/  proxy/  agent/  .claude/  stacks/php-htmx/  apps/

  4. Régler l'instance

    cd ~/mon-instance
cp .env.example .env
nano .env
    VariableÀ mettre
    APPS_HOSTl'hôte de l'étape 2, par exemple apps.tondomaine.fr
    HOST_UID, HOST_GIDle résultat de id -u et id -g. Les conteneurs tournent sous cet utilisateur : les fichiers de data/ t'appartiennent.
    STACKFAST_INSTANCEmain. À changer seulement si deux instances partagent la machine.
    plus tardBACKUP_PASSPHRASE pour chiffrer les sauvegardes ; AGENT_CLAUDE_CODE_OAUTH_TOKEN pour les agents.

  5. Vérifier

    stackfast          # liste les commandes
stackfast ls       # « aucune app » : normal, il n'y en a pas encore

    Les commandes d'instance marchent depuis n'importe quel sous-dossier de l'instance.

Tu as déjà un Caddy ou des projets sur ce serveur ?

Le Caddy de stackfast ne peut pas démarrer tant qu'un autre tient les ports 80 et 443. Fais d'abord une sauvegarde de tes projets actuels, puis arrête-les sans les supprimer (docker stop, et docker update --restart=no pour qu'ils ne reviennent pas au redémarrage). Leur migration, un projet à la fois, est décrite dans docs/DEPLOY-VPS.md (section 7) et docs/SAUVEGARDE.md du hub.

Quelle version ?

Les commandes backup, restore et agent viennent de la branche stack-agents. Si stackfast backup répond « commande inconnue », cette branche n'est pas encore fusionnée dans main : fusionne-la, puis stackfast pull (le hub) et stackfast sync dans l'instance.

Premier projet

De rien à une page en HTTPS, puis à un vrai nom de domaine.

Créer l'app

stackfast new php-htmx monsite

Le slug (monsite) est le nom court de l'app : lettres minuscules, chiffres et tirets. Il est unique dans l'instance. Voici la chronologie complète de cette commande.

À l'écran :

créée      : apps/php-htmx/monsite
token      : MONSITE_API_TOKEN (bearer /api + /mcp), dans apps/php-htmx/monsite/.env
en ligne   : monsite → https://apps.tondomaine.fr/monsite/
QuandDurée mesuréePourquoi
La première app d'une stackenviron 1 minutel'image de la stack est construite une fois (PHP, extensions, Caddy intégré).
Chaque app suivanteenviron 8 secondesl'image est réutilisée : seuls le gabarit et le conteneur sont créés.

Vérifier

curl -I https://apps.tondomaine.fr/monsite/
stackfast ls
stackfast logs monsite
APP      STACK      ÉTAT              ADRESSE
monsite  php-htmx   running healthy   https://apps.tondomaine.fr/monsite/

Le premier accès peut prendre quelques secondes : c'est le moment où Caddy obtient le certificat.

Construire le site avec Claude Code

Ce que tu as à cet instant est un gabarit : une petite liste d'éléments, avec son API et ses tests. Le contenu du site, c'est le travail de Claude Code, lancé dans le dossier de l'instance. Il lit AGENTS.md (le contrat de l'instance), puis celui de la stack, puis celui de l'app.

cd ~/mon-instance && claude
# dans Claude Code :
/new-app php-htmx monsite       # remplit le PRD avec toi, une question à la fois
/feature ajouter la page contact

Voici ce que contient l'app, et à quoi chaque fichier sert :

apps/php-htmx/monsite/
  PRD.md          # ce que l'app doit faire : ce qui n'y est pas n'existe pas
  AGENTS.md       # règles propres à l'app, et ses leçons
  index.php       # routes : une ligne par action
  lib/            # le métier, en fonctions pures (aussi la future surface /api et /mcp)
  views/          # pages, et fragments htmx dans views/partials/
  data/           # JSON, jamais servi ni commité
  tests/          # *_test.php, lancés par stackfast check
  compose.yml     # son conteneur (la base commune vient de la stack)
  .env            # ses secrets, jamais commité
Le hook de fin de tour

À la fin de chaque tour, Claude Code relance stackfast check sur les apps touchées. Si un test est rouge, Claude est bloqué et voit l'erreur : il ne peut pas annoncer « terminé » sur du rouge sans que tu le voies.

Lui donner un nom de domaine

L'adresse de test apps.tondomaine.fr/monsite/ est faite pour l'incubation. Quand le site est prêt, il passe sur son propre nom en une commande, sans toucher au code.

  1. Pointer le DNS

    Ajoute un enregistrement A (et AAAA) pour monsite.fr vers l'IP du serveur, comme à l'étape 2 de l'installation.

  2. Le dire à stackfast

    stackfast domain monsite monsite.fr

    La commande écrit proxy/domains, régénère la config de Caddy, la valide, puis la recharge sans coupure. Le certificat est demandé au premier accès.

Tu peux enchaîner les adresses : apps.tondomaine.fr/monsite/, puis monsite.tondomaine.fr, puis monsite.fr. À chaque étape, les adresses précédentes redirigent en 301, donc aucun lien ne casse. stackfast domain monsite sans argument affiche l'adresse actuelle ; --rm retire un domaine.

Pourquoi le code ne change pas

L'app ne connaît jamais son adresse. Elle écrit ses liens avec url('/items'), qui s'appuie sur l'en-tête X-Base-Path posé par Caddy : /monsite en incubation, / sur un domaine. Le proxy écrase toujours cet en-tête : un client ne peut pas le choisir.

Vie du projet

Le site est en ligne. Voici ce que tu fais ensuite, du plus courant au plus rare.

Modifier et déployer

Le code de l'app est monté dans son conteneur et lu à chaud : modifier un fichier PHP ne demande ni build ni redémarrage. Le code vit dans le dépôt git de l'instance. Tu le modifies sur le serveur avec Claude Code, ou en local puis git push et stackfast deploy sur le serveur (git pull, puis chaque app mise à jour et le proxy régénéré). Donne à ce dépôt un remote privé : c'est la copie de ton code.

Tu changesTu lances
un fichier de code (index.php, lib/, views/)rien : c'est lu à chaud
le .env ou le compose.yml d'une appstackfast up monsite
du code sur un autre postegit push, puis stackfast deploy sur le serveur
une stack ou stackfast lui-même (dans le hub)stackfast pull, puis dans l'instance stackfast sync et stackfast deploy

sync s'arrête si quelqu'un a modifié à la main un fichier posé par le hub (il liste lesquels). --force les écrase.

Regarder ce qui se passe

stackfast ls                  # apps, santé, adresses
stackfast logs monsite -f     # journaux, erreurs PHP comprises
stackfast shell monsite       # un shell dans le conteneur, avec les droits de l'app
stackfast check monsite       # lint + tests dans un conteneur jetable, sans réseau

Faire travailler des agents

Pour avancer plusieurs chantiers en parallèle, tu lances plusieurs agents Claude Code sur la même app. Chacun reçoit une copie de l'app dans une sandbox : il peut tout casser chez lui, il ne voit ni les autres apps, ni les .env, ni Docker.

stackfast agent new monsite a1 a2 a3                      # trois sandboxes (la première construit l'image)
stackfast agent run monsite a1 "ajoute un export CSV"      # autonome, en arrière-plan
stackfast agent shell monsite a2                           # ou une session interactive
stackfast agent ls                                         # état, fichiers changés, adresse de preview
stackfast agent diff monsite a1                            # ce qu'il a changé
stackfast agent apply monsite a1                           # fusion à 3 voies dans l'app, après ta relecture
stackfast check monsite && git commit                    # preuve, puis commit
  • Chaque agent a une preview à https://apps.tondomaine.fr/_preview/monsite/a1/, sous mot de passe (affiché une fois, stackfast agent passwd pour le changer).
  • apply ne copie que ce qui est dans apps/<stack>/<slug>/. Deux agents qui touchent le même fichier se fusionnent ; une même ligne modifiée donne un conflit signalé par des marqueurs, et stackfast check refuse de passer tant qu'il en reste.
  • Pour qu'un agent travaille, donne-lui un compte : AGENT_CLAUDE_CODE_OAUTH_TOKEN (issu de claude setup-token) ou AGENT_ANTHROPIC_API_KEY dans le .env de l'instance.
Ce que la sandbox ne garantit pas

L'agent a accès à Internet (il lui faut l'API Claude). Ce qu'il voit, son code et sa clé, peut sortir si une injection de prompt le lui fait faire. Aucun secret de production dans une sandbox, et une clé API dédiée aux agents. agent run lance Claude sans confirmations : la sandbox est la frontière, pas les questions. Détails dans docs/AGENTS-ISOLES.md.

Sauvegarder et restaurer

Le code est dans git. Les data/ et les .env n'y sont pas : ils n'existent que sur le serveur. stackfast backup les met, avec la config d'instance et les certificats, dans une archive.

stackfast backup                        # → backups/main-2026….tar.gz (chiffrée si BACKUP_PASSPHRASE)
stackfast backup --keep 14              # garde les 14 dernières
stackfast restore <archive> --list      # voir le contenu sans rien toucher
stackfast restore <archive> monsite    # une app : ses data/ et son .env
stackfast restore <archive> --certs    # tout, certificats compris (serveur neuf)

Une sauvegarde sur le même disque ne protège pas d'une panne du serveur. Mets-la en cron, puis copie-la ailleurs :

0 3 * * * cd ~/mon-instance && stackfast backup --keep 14 && rsync -a backups/ moi@autre-machine:sauvegardes/

Serveur détruit ? Installe Docker et stackfast, récupère le code (git pull), copie l'archive, puis stackfast restore <archive> --certs. Dans le test de sinistre (conteneurs, volumes, images, .env et données supprimés), tout est revenu en 16 secondes, avec le même certificat. Ce qui est remplacé n'est jamais écrasé : l'ancien état va dans backups/pre-restore/. stackfast audit te signale l'absence de sauvegarde récente.

Appliquer un correctif de sécurité

Quand une faille PHP est annoncée (comme PHP2Shell, en octobre 2026, corrigée en 8.5.12), la procédure tient en deux commandes, sur chaque serveur :

stackfast audit      # « PHP 8.5.11 : OBSOLÈTE, 8.5.12 est publié »
stackfast update     # reconstruit, teste toutes les apps, bascule, puis audit
  • La branche PHP est fixée dans stack.conf (8.5), le correctif ne l'est pas : update reconstruit avec le dernier PHP 8.5.x publié.
  • Un conteneur déjà lancé garde l'ancien PHP en mémoire. C'est pourquoi update recrée chaque conteneur, et pourquoi audit signale ceux qui tournent encore sur l'ancienne image, apps et agents compris.
  • Si l'image amont n'a pas encore le correctif (php.net publie parfois quelques heures avant), audit le dit. En attendant, les réglages de durcissement de la stack sont déjà actifs, et tu relances update plus tard.
  • Mets stackfast audit en cron : il sort en erreur dès qu'il y a une action à faire.

Arrêter une app

stackfast down monsite     # arrête le conteneur et son réseau ; fichiers et data/ restent
stackfast up monsite       # la relance

Il n'existe pas encore de commande pour supprimer définitivement une app : retire son dossier avec git, puis stackfast domain monsite --rm <domaine> et stackfast proxy.

Testé sur un vrai Docker

Création d'app, parcours des trois adresses, isolation entre apps, conteneur durci, check, audit et update avec un vrai PHP 8.5.11 vulnérable, rollback, trois agents en parallèle avec fusion et conflit, backup et restore avec sinistre simulé.

Pas encore éprouvé

Un vrai serveur avec un DNS public : l'obtention des certificats Let's Encrypt et l'ouverture des ports 80/443 depuis Internet. Claude Code avec un vrai compte dans une sandbox d'agent. stackfast migrate sur un ancien serveur dont les conteneurs tournent. Le premier déploiement réel est donc aussi le test de ces trois points : garde l'ancien état de côté jusqu'à ce qu'ils passent.
